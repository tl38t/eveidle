## 一、结论先行

| 判定项 | 结论 |
|---|---|
| 逻辑层可复用度 | **100%**（`core` + `systems` + `data` = 51,880 行，零 DOM 依赖，可原样搬进小游戏） |
| UI 层可复用度 | **0%**（`js/ui` 18,444 行 + `index.html` 474 个 div / 475 个 id，全部依赖 DOM，微信小游戏无 DOM） |
| 能否"改一次三平台生效" | **逻辑层：能（现状即是）；UI 层：不能**——除非抽 UI 原语层（见 §5.3，成本高，非一期目标） |
| 能否不影响 Steam / TapTap 封包 | **能**，但必须显式加构建排除规则（见 §5.1，这是最容易被忽略的静默破坏点） |
| 最大风险 | 不是技术，是**工作量**（UI 重写）与**主包 4MB** 硬限制 |
| 推荐路线 | **C：自研轻量 Canvas 2D UI 框架 + 先做核心循环精简版**，拒绝 mini-DOM，暂不引擎化 |

一句话：**这是一次"逻辑层白送、UI 层重做"的迁移**。逻辑层 5.2 万行可以直接跑进微信，真正的成本全在 1.8 万行 HTML UI 的重建，以及主包 4MB 的瘦身。

### 2.3 已有平台抽象（可直接扩展）

```
js/platform/
├── platform-runtime.js          # 集中工厂，getPlatform() → "taptap" | "steam" | "web"
├── *-contract.js                # 5 个契约基类（云存档/成就/本地镜像/排行榜/广告）
├── providers/                   # noop 实现
├── steam/                       # Steam provider
└── taptap/                      # TapTap provider
```

- 设计模式：**契约基类 + 工厂**，不是注册表。
- `getPlatform()` 全项目仅 **5 处**依赖，业务层走 provider 多态，不判平台字符串 —— 耦合极低，加第四个平台（`wechat`）成本低。
- ⚠️ 硬约束：新平台脚本必须在 `index.html` 中**早于 `js/core/persistence.js`** 加载；`tools/verify.mjs` 有顺序断言。

## 三、微信小游戏硬约束（2026-09 官方口径）

### 3.1 运行时约束

| 约束 | 上限 / 现状 | 影响 |
|---|---|---|
| **DOM / BOM** | ❌ 完全没有 `document` / `window`（iOS JavaScriptCore / Android V8） | 决定性问题，见 §4 |
| `weapp-adapter` 覆盖范围 | 仅 `canvas` / `image` / `Audio` / `XHR` / `localStorage` / `WebSocket` | **不覆盖 HTML 布局与 CSS**，官方明说"对浏览器环境的模拟远不完整" |
| **主包** | ≤ **4 MB** | 现有 7.8 MB JS + 8.7 MB 资源，必须大幅瘦身 |
| **分包总和** | ≤ **30 MB** | 成就图等可放分包 |
| **storage 单 key** | ≤ **1 MB** | 主存档 key `eve_idle_save` **高危**，见 R2 |
| **storage 总计** | ≤ **10 MB** | 同上 |
| 网络域名 | 需配置 request 合法域名白名单 | 现有云函数 / 联盟 API 域名需备案登记 |
| 动态执行 | 禁用 `eval` / `new Function` | 本项目未使用 ✅ |
| `Blob` | 不支持 | 3 处需改造 |

> 容量破局点：除 storage 外，微信提供 `wx.getFileSystemManager()` 文件系统（用户文件空间约 200 MB），**大存档应走文件系统而非 storage**。

### 3.2 合规约束

| 项 | 要求 | 周期 |
|---|---|---|
| ICP 备案（小程序备案） | 强制，所有游戏都要 | 10–30 工作日 |
| **软著证书** | ⚠️ **IAA（纯广告变现阶段不需要）** —— 走「著作权自我声明」扫码签署即可。**仅 IAP（内购）为必填**。例外：仅在①游戏名含英文或"软件"字样 ②涉及品牌/公众人物合作时才需提交证书（本项目均不触发） | 若需：30–60 工作日 |
| 小游戏备案 | 无版号通道需走 | 10–20 工作日 |
| 游戏自审自查报告 | 强制 | 自行填写 |
| 适龄提示（8+/12+/16+） | 强制 | 平台审核 |
| **版号** | **仅在做内购（IAP）时必需**；纯广告变现（IAA）平台准入可豁免 | 若需：4–6 个月 + 企业主体 + ICP 许可证 |

**关键决策**：项目现有广告系统（`ad-service.js`、广告 buff）。若微信版走**纯 IAA 广告变现**，则**无需版号**，个人主体即可上线；若要内购，则必须企业主体 + 版号，周期半年起。这直接决定主体注册策略，见 §7 决策点 3。

### 3.3 软著专项（2026-09-13 更正：IAA 通道不需要软著证书）

> ⚠️ **更正说明**：初版称"软著是微信小游戏上架强制资质、纯广告变现也要" —— **此说法错误**。经查微信开放平台《小游戏备案·资质提交及审核》官方文档，IAA 与 IAP 的软著要求并不相同，现更正如下。

**微信官方文档原文（服务市场《小游戏备案 - 资质提交及审核》）**：

- **情况一（IAP 游戏）**：已开通或需开通虚拟支付。材料 1 网络游戏出版物号核发单（必填）+ **材料 2 计算机软件著作权登记证书（必填）**。
- **情况二（IAA 游戏）**：当前及未来均不开通虚拟支付。材料 1 代备案授权书（扫码签署）+ **材料 2 著作权自我声明（扫码签署）**+ 材料 3 游戏自审自查报告（线上确认）。**无软著证书要求**。
- **例外触发**：选择情况二时，**仅**当 ①游戏名称含**英文**或**"软件"字样** ②涉及**品牌 / 公众人物合作**，才需补交《计算机软件著作权登记证书》或对应授权材料。

**本项目判定**：游戏名《深空放置：边疆纪元》—— 含英文字母 **0** 处、含"软件"字样 **0** 处、无品牌/公众人物合作 ⇒ **不触发任何例外，走 IAA 通道无需软著证书**。

**软著仅在以下情形才需要**（IAA 均不涉及）：

| 项 | 内容 |
|---|---|
| 全称 | 计算机软件著作权登记 |
| 发证机构 | 中国版权保护中心 |
| 保护对象 | 代码的表达形式（不保护玩法规则） |
| 费用 | 官方已停征（申请费、证书费全免）；代理加急另收费 |
| 材料（2026 从严） | 申请表（功能描述 500–1300 字）、源代码**前 30 页 + 后 30 页**（每页 ≥50 行）、说明书（含流程图 + 界面截图，≥500 字）、签章页**本人亲笔手抄诚信承诺** |
| **何时才需要** | ① 改走 **IAP 内购（必填）** ② 游戏名含英文 / "软件"字样 ③ 涉及品牌或公众人物合作 |
| 仍建议办理的理由 | ① 是版号申请的前置条件，政策若收紧不必从零开始 ② 版权维权核心凭证，被抄袭时无软著难以主张权利。周期 30–60 工作日，可与开发并行 |
| 复用可能 | 若此前为 Steam / TapTap 上架已办过软著，且**主体与名称均与本次一致**，可直接复用。截至 2026-09-12 仓库内未发现任何软著资料 |

**若决定办理软著，三条风险**：

1. **名称一致性**——软著名、游戏内标题、版号申报名三者必须一字不差，差一个字即返工（§9 R10）。
2. **2026 新政**——由"形式审查"转为"有限实质审查 + 诚信监管"，补正率升至 60%+。
3. ⚠️ **AI 生成代码风险**——纯 AI 生成代码可能被认定"无独创性"而驳回，且签章页涉及"非 AI 生成"的诚信承诺。本项目为 AI 重度参与开发（172,965 行中相当比例由 AI 产出），**此风险必须在申请前与代理机构确认实操口径，不得在诚信承诺上作不实陈述**。

**合规线时间轴（纯 IAA 通道，更正后）**：

```
微信认证 + 主体材料 → ICP 备案（小程序备案）10–30 日 → 资质审核（IAA）1–2 日
  → 小游戏备案 10–20 日 → 版本审核 → 发布
```

微信官方给出的 IAA 通道**平台侧审核时效为 13–37 个工作日**；叠加 ICP 备案 10–30 工作日，**整体约 1.5–2 个月，且全部可与开发并行**。

> ✅ **关键变化**：软著不再是 IAA 的串行瓶颈。旧估「93 工作日（≈4.5 个月），含软著 60+ 日」**已作废**。
> ⚠️ 但 IAA 免版号是**平台准入层面的豁免**，不等于法规明确免审。政策存在收紧可能（抖音 2024 年曾要求部分品类补版号或软著）。建议把软著定位为**预备项而非阻塞项**。

### 3.4 ⚠️ 主体与类目限制（2026-09-13 新增，**比软著更硬的约束**）

**结论前置**：在**资质材料层面 IAA 确实几乎没有门槛**（无版号、无软著，见 §3.3）—— 这点已核实无误。但门槛转移到了另外两处：**① 发布链路反而比 IAP 更长 ② 类目受限**。

#### 3.4.1 官方 IAA 发布流程全链路（developers.weixin.qq.com/minigame/introduction/guide/iaa）

```
注册账号 → 名称/简称/头像 → 类目设置
   → 微信认证 ‖ 适龄提示设置 ‖ 资质审核
      → 版本审核 ‖ 小游戏备案 → 小程序备案
         → 小游戏发布
```

官方「流程指引」原文注意事项：

> 1. 游戏开发可以在和下列流程同步进行，无需等待审核相关流程
> 2. 根据你设置的游戏类目，流程会有一些差别，**文化互动类**的版本审核必须在资质审核完成之后，其他类目则可以同时进行
> 3. 版本审核可以和小程序备案支持并行提交

#### 3.4.2 ⚠️ 反直觉事实：IAA 比 IAP 更慢

官方《小游戏接入指南》总目录页原文：

| 通道 | 审核时效 |
|---|---|
| **（1）不开通虚拟支付游戏（IAA）** | 预计需 **13 – 37 个工作日** |
| （2）开通虚拟支付游戏（IAP） | 预计需 9 – 22 个工作日 |

**IAA 反而比 IAP 慢 4–15 个工作日**。原因：IAA 无版号批复文件，**必须走完"小游戏备案"的主管部门审核环节**（平台初审 1–2 工作日 + 主管部门 10–20 工作日）；而已提供版号批复的 IAP 游戏可豁免该环节。

> 修正：初版估「IAA 约 1.5–2 个月」在方向上正确，但需注意这是**行政等待**，与开发可完全并行，不构成人力成本。

#### 3.4.3 微信认证：个人主体可以做（纠正一条第三方误传）

官方《微信认证》页列有 **「小程序微信认证申请流程指引（个人）」** 与「（非个人）」两套并行入口 ⇒ **个人主体是可以微信认证的**。第三方博客流传的"个人主体不支持微信认证"**不准确**。

官方总目录页注意事项原文：

> **企业主体**必须进行微信认证才能提交小程序备案

—— 该句仅对企业主体作强制要求，反证个人主体无此强制。

#### 3.4.4 ⚠️ 唯一实质硬约束：类目

**微信官方《类目设置》原文**（developers.weixin.qq.com/minigame/introduction/guide/type）：

> 一级类目，不支持修改，且小游戏账号只有"游戏"这个类目（注册时勾选），无法更换或删除，如选择错误只能重新注册
> 二级类目，小游戏申请时填写，发布前都可以修改（文化互动类目除外），发布后不可修改
> **个人主体，暂不支持选择文化互动、角色类和牌类三种类目**
> 注意：如二级游戏类目与实际游戏内容不符，**将会在提审版本时驳回**，请谨慎选择

**微信开放社区官方运营答复**（置顶帖）：

> 问：个人主体，可以发布二级类目为角色的吗？
> 答（小游戏运营专员 - 宏）：**个人主体暂不支持开发角色类目游戏**。

**"角色类"的实际判定范围**（社区案例归纳）：卡牌、MMO、ARPG、回合制、**战争策略**均在角色类内。

**本项目判定 —— 存在双向可能，不能下定论**：

| 特征 | 指向角色类 | 指向休闲类 |
|---|---|---|
| 舰船 / 装备 / 模块装配 | ⚠️ 装备驱动成长 | — |
| 脑插技能树、研究科技树 | ⚠️ 养成线 | — |
| 战斗、星图、虫洞试炼 | ⚠️ 关卡推进 | 全自动、无实时操作 |
| 生产 / 制造 / 冶炼 | — | ✅ 经营属性 |
| 放置挂机（离线结算） | — | ✅ idle 品类典型特征 |

> ⚠️ **诚实结论**：放置类（idle）在微信小游戏生态中**既有归"休闲"的先例，也有因装备/养成线被判"角色"的先例**。判定权在审核员，无法从文档推断出确定答案。
> **建议动作**：提审前通过微信开放社区发帖或直接联系平台侧，**就本游戏的具体内容确认二级类目归属**，再决定主体类型。

**社区实证案例**（微信服务市场，2023-08-16）：

> "花了大半年做的游戏，**被判定为角色扮演类，无法上架**！直接原地去世！！"

**结论与对策**：

| 主体 | 能否上架本项目 | 代价 |
|---|---|---|
| **个人主体** | ⚠️ **取决于类目判定**：若归"休闲"✅；若归"角色"❌ | 注册免费、可微信认证；风险是判定翻车则前功尽弃 |
| **个体工商户** | ✅ 均可（不受三类目限制） | 营业执照 + 微信认证（个体户价）；不能办网文证/ICP 证 |
| **企业主体** | ✅ 均可 | 营业执照 + 微信认证 300 元/年 |

> ⚠️ **主体类型注册后变更代价高**，且一级类目选错只能重新注册。立项前必须先定主体。
> 💡 **风险最低路径（无资产顾虑时）**：直接注册**个体工商户**（成本极低、无类目限制、可开票），把"类目判定翻车"这一不确定性彻底消除。
> ⚠️ **但用户为在职、有工作者**（见 §3.4.5）：个体工商户的**无限责任**会波及个人家庭资产，叠加劳动合同/竞业限制风险。若用户在意资产隔离，**有限公司反而是更省心的选型**（有限责任 + 仅约 2000–3000/年代账成本）。主体决策须结合"是否在职 + 是否介意个人资产兜底"两项一并定。
> ⚠️ **待确认**：有第三方来源称「企业主体做纯 IAA 也要求软著」，与官方《资质审核(IAA)》文档冲突。**提审前需向微信平台侧核实企业主体 + IAA 的软著要求**。

#### 3.4.4.1 ✅ 2026-09-13 核实：个人主体可开通流量主做 IAA（纠正此前隐含担忧）

**此前隐含担忧"个人主体可能无法接广告"经检索证伪**：

| 来源（2026） | 结论 |
|---|---|
| 腾讯云开发者社区《微信小游戏完整开发指南》 | "个人开发者不能做付费功能，**只能靠广告**"、"需要 500 独立用户才能开通流量主" |

**个人主体做 IAA 的真实边界（硬限制不变）**：

- ✅ 可注册小游戏、上线纯广告游戏、UV≥500 后开通流量主接 Banner/激励视频/插屏广告
- ❌ **类目受限**：不能选"角色类/文化互动/牌类"（这就是 R12 类目判定风险的来源——个人主体必然触发该限制，企业/个体不受限）
- ❌ 不能内购（IAP 虚拟支付需企业/个体）
- ❌ 2026 收紧项：不能加客服微信、不能配置订阅消息长期模板、不能直播

#### 3.4.4.2 📌 用户决策（2026-09-13）：个人主体先试，不行再说

用户确认：**先以个人主体走 S0 行政验证流程**，若后续（类目被驳 / 需内购 / 需资产隔离）再升级为企业或个体工商户。

**据此调整 S0 路径**：

- 个人主体注册**无需营业执照、无需对公账户**，仅需管理员身份证 + 微信扫码实名 → S0 行政验证门槛与耗时大幅降低（即点即走）
- 名称查重、定主体、注册、类目、资质审核(IAA)、备案仍可走通（§3.5.4）
- 仍须面对 **R12 类目判定风险**（个人主体不能选角色类）——这是"个人先试"唯一可能翻车的点，验证手段仍是 §3.5.3 的 S1 最小原型或开放社区确认
- **主体升级路径预留**：若 S1 类目被驳或未来要内购/资产隔离，个人账号可重新注册企业/个体账号（原个人账号不浪费，可作测试号保留）

#### 3.4.5 ⚠️ 在职员工额外约束（2026-09-13 补充，用户为有工作者）

**背景**：用户当前有正式工作，是否注册个体户/公司直接影响其劳动、税务、资产安全。**本小节结论来自法规检索（非法律意见）**。

**① 无限责任（最关键，决定主体选型）**

- 个体工商户**无独立法人资格**，债务由经营者**个人全部财产**承担（《民法典》第56条）；法院可直接冻结经营者**个人**银行账户，无需追加程序（最高法执行规定第13条）。
- 有限公司则为**有限责任**（注册资本为限），公司债不波及个人车/房/存款。
- ⇒ 对「有工作、有正常家庭资产」的用户，**有限公司的资产隔离价值高于个体户省下的成本**。

**② 劳动合同 / 竞业限制**

- 在职员工天然负有「忠诚义务」：个体户业务若与本职**竞争**或占用工作时间，公司可解雇并索赔；若劳动合同含"禁止兼职/经商"条款则更危险。
- 游戏行业 vs 本职工作：仅当本职亦属游戏/互联网竞品时构成冲突；不相关行业通常无碍。
- **立项前动作**：翻看劳动合同是否含"禁止兼职/经商/竞业限制"条款；评估本职与游戏业务是否竞争。

**③ 税务申报（可控）**

- 经营所得（5%–35% 超额累进）与工资薪金**分账单独申报**；月销售额 < 10 万免增值税，但须申报。
- 只要合规申报，无额外风险。

**④ 社保 / 年报（低风险）**

- 上班的**职工社保照常交，个体户注册不触发中断**；个体户不强制另交社保。
- 每年 6/30 前必须做工商年报，漏报进"经营异常名录"。

**对 §3.4.4 主体对照表的修正建议**：

| 主体 | 在职用户适配度 | 关键取舍 |
|---|---|---|
| 个人 | 看类目判定（同前） | 零责任零申报；但类目受限、不能开票/内购 |
| 个体工商户 | ⚠️ 能发但有个人资产兜底风险 | 解锁类目+开票；承担无限责任 + 申报 + 年报 + 本职冲突风险 |
| **有限公司** | ✅ **资产隔离最干净** | 有限责任护住个人资产；代价 = 认证 300/年 + 代理记账约 2000–3000/年 + 对公账户 |

> 💡 **修正结论**：此前"优先个体户"的建议，在已知用户在职且有资产后，**应改为优先评估有限公司**——多花少量年费，买断个人连带责任。个体户仅在"确信无资产风险、且不愿负担代账成本"时优先。

#### 3.4.6 ⚠️ 新发现：游戏名可能被"同名驳回"（官方 Q&A 原文）

《小游戏备案》页 Q4：

> **Q4：小游戏备案因"同名游戏已获批 / 与已获批名称存在重复"被驳回？**
> 原因在于游戏名已被其他游戏使用并获得前置审批主管部门通过。主管部门须确保游戏名称与备案编号对应的唯一性，**目前暂不支持相同游戏名称重复获批，请修改游戏名称后重新提交审核**。
> 改名后须确保小游戏备案中填写、资质材料刊载的游戏名称与改名后一致，**新名称与游戏内容玩法存在关联性**。

⚠️ **影响**：《深空放置：边疆纪元》存在被占用或判定重复的可能。**必须在注册前先查重**（可联系官方智能客服确认），否则备案阶段被驳回要改名，而改名会连锁影响已签署的资质材料。

**名称与主体的"锁定效应"**（官方原文，务必重视）：

> 审批要求游戏名称、账号主体在任何阶段都保持与当前提审游戏名称、提审账号主体一致，否则会导致驳回。
> 【小游戏备案】提交后处于审核中或审核通过，**不允许修改名称或账号主体**。
> **改名或主体迁移将极大影响你的备案时效和结果，请务必谨慎操作。**

⇒ **结论：名称与主体必须在注册阶段一次性定死，中途改动代价极大。**

#### 3.5.2 ⚠️ 策略缺口：最大的风险恰恰无法提前验证

官方《类目设置》原文：

## 四·补、替代平台选项（低成本路线，2026-09-12 增补）

> 触发原因：微信方案的总成本中，**UI 重写（约 90 人日）远大于合规等待（IAA 通道约 1.5–2 个月，且可并行）**。
> 若改用**保留 Web 运行环境**的平台，UI 重写成本**直接归零**。以下为核查结果。

### 4.5.1 关键认知

**国内所有小游戏平台（微信 / 抖音 / 快手 / 支付宝 / QQ）均为无 DOM 环境 + 需平台备案**（IAA 通道免版号、免软著证书，见 §3.3）—— 在它们之间切换**不会降低任何成本**（真正的成本是 1.8 万行 UI 重写）。
能绕开 UI 重写的只有两条路：**① 留在 Web 环境；② WebView 打包**。

### 4.5.2 平台对比（2026-09 核查）

| 平台 | 代码改动 | 软著 / 版号 / 备案 | 上线周期 | 自带流量 | 备注 |
|---|---|---|---|---|---|
| **itch.io** | **约 2 人日** | **全不需要** | **几分钟** | 无，需自导 | 上限：1000 文件 / 500 MB / 单文件 200 MB |
| **PWA 自有站** | 约 3 人日 | 国内仅域名 ICP 备案（免费，7–20 天）；用海外域名可免 | 1–3 周 | 无，需自导 | 手机"添加到桌面"，体验接近 App |
| **Google Play** | 约 10 人日（Capacitor 壳） | **全不需要**（$25 一次性 + 政府 ID） | 2–4 周 | 全球安卓最大商店 | 新个人账号需 **12 人 × 14 天**封闭测试（2024-12-11 由 20 人下调） |
| **CrazyGames / Poki** | 约 15 人日（接 SDK + 过 QA） | 全不需要 | 1–2 月 | 5000 万 / 1 亿月活 | 需接其 SDK 并通过质量与合规审核 |
| 微信小游戏 | 约 90 人日 | 全需要 | 3–6 月 + 93 工作日 | 微信生态 | 见 §4 |

**总投入估算（人日，含合规等待折算）**：itch.io 2 / PWA 5 / Google Play 15 / CrazyGames 20 / **微信 180**。

### 4.5.3 itch.io 适配性核查（已实测）

| 限制项 | itch.io 要求 | 本项目实测 | 结论 |

### 4.5.4 建议

若目标是**快速获得移动端/国际用户**而非"必须进微信生态"，优先顺序应为：

## 五、架构设计：如何满足两个硬要求

### 5.1 要求 1：不能影响现有 Steam / TapTap 封包

**核心风险**：`build-taptap-h5.mjs` 用 `git archive` 打包**整个仓库**。新增微信工程目录会被静默打进 TapTap 包 —— 包体变大，且 `auditAssetRefCoverage` 资产引用对账可能报警。Steam 侧 `package-steam.cjs` 同理。

**落地措施（三道锁）：**

| # | 措施 | 位置 |
|---|---|---|
| 1 | 微信全部产物隔离在独立目录 `wechat/`、`js/platform/wechat/`、`tools/build-wechat-mg.mjs`，**不进入 `index.html` 的任何 `<script src>` / `<link href>`** | 新增目录 |
| 2 | 在 `build-taptap-h5.mjs` 的排除规则中追加 `wechat/`、`js/platform/wechat/`（与现有排除 `js/platform/steam/` 同一机制） | 改 1 行 |
| 3 | 在 `electron/package-steam.cjs` 同步加排除 | 改 1 行 |

**为什么强调不进 `index.html`**：`tools/verify.mjs` 硬断言 `scriptSources.length === 120`、`styleSources.length === 5`。任何新增的被 `index.html` 引用的微信脚本/CSS 会**直接让构建失败**。这是设计上的天然隔离 —— 微信代码必须走独立入口，反而保证了零干扰。

**验收方式**：改动后连续构建两次 TapTap / Steam 包，比对 SHA-256 与字节数必须与改动前**完全一致**（现有脚本已有两遍构建比对能力）。

### 5.2 要求 2：修 bug 要三个平台一起修

分两层说清楚，这个边界必须提前接受：

| 层 | 代码位置 | 三平台是否一起修 |
|---|---|---|
| **逻辑层** | `js/core`（18,827）+ `js/systems`（23,184）+ `js/data`（9,869）= **51,880 行** | ✅ **是，且现状即是**。三平台共用同一份源码，改一次全生效。 |
| **UI 层** | `js/ui`（18,444）+ `index.html` | ❌ **否**。Web 端（Steam/TapTap）与微信端是两套渲染实现，UI bug 要改两处。 |

这是物理约束，不是设计选择 —— 因为微信没有 DOM，`js/ui` 的代码在微信里一行都跑不了。

**但可以通过"把逻辑挤出 UI 层"来缩小这个面积**：
- 现状 `js/ui` 里混了不少业务判断（例如 `shell-render.js` 404 处 DOM 命中里夹杂状态计算）。
- 迁移过程中把这些计算逐步下沉回 `js/systems`，UI 层只留"取数据 → 画"。
- 下沉的部分自动变成三平台共用，等于**顺手改善了整个项目的分层**。

### 5.3 终态（可选，非一期）：UI 原语层

若要求"UI 也改一次三平台生效"，唯一解是抽 UI 原语：

```
业务 UI 代码（写一次）
        ↓
UI 原语接口：Panel / List / Button / ProgressBar / Modal / Tab / Grid
        ↓                ↓
Web 实现（DOM）      微信实现（Canvas 2D）
```

代价：现有 18,444 行 DOM UI 需重构到原语上。**建议列为终态目标，一期不做** —— 先让微信版跑起来，再谈抽象。

### 5.4 三平台构建矩阵（目标态）

```
                    单一 codebase（main 分支）
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
  build-taptap-h5.mjs   package-steam.cjs    build-wechat-mg.mjs
   排除 steam/、wechat/   排除 wechat/         排除 steam/、taptap/
   注入 taptap provider   注入 steamworks       注入 wechat provider
        │                     │                     │
     TapTap ZIP          Steam 包（Electron）   小游戏工程（game.js）
```

`build-wechat-mg.mjs` 的关键能力：从 `index.html` **解析现有 script 顺序**并生成 `game.js` 的 `require` 链。这样加载顺序永远以 `index.html` 为唯一真值源，不会因为手写清单而漂移（项目记忆里已有"白名单与目录清单是两把独立的锁"的教训，此处用自动生成规避）。
